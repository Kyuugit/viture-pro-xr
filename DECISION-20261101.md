# Consolidated recommendation — original VITURE Pro XR

Date: 2026-11-01. Status: **research recommendation; owner decisions and empirical validation pending**. This record consolidates the existing packet and the new continuation rather than restarting the survey. It does not authorize local actions.

## Decision

Adopt **host-side HDR-content presentation as the delivery path**, run **full-resolution SBS refresh qualification as a separate workstream**, and retain **native PQ as a bounded, evidence-gated investigation**. Do not make a firmware unlock, native 10-bit panel claim or a particular refresh rate a prerequisite for useful results.

This choice maximizes work supported by inspectable implementations while keeping the uncertain hardware questions testable. It does not conclude that native HDR or higher refresh is impossible. No new optical or device measurements were performed. The approximately 93/95 Hz recollection remains provisional and supplies neither a validated operating point nor a ceiling.

Supporting evidence is frozen at [bin commit 1f312101161d279b00713ac3d8c4cab79962cbff](https://github.com/Kyuugit/bin/tree/1f312101161d279b00713ac3d8c4cab79962cbff/viture-pro-xr-hdr-refresh-20261029). The [living archive index](https://github.com/Kyuugit/bin/blob/main/viture-pro-xr-hdr-refresh-20261029/README.md) tracks subsequent additions. Future project decisions, code and results belong in this repository; supporting research stays in that bin folder.

### 1. Better presentation of HDR content

| Workload / priority | Candidate | Recommendation and trade-off |
|---|---|---|
| First: controlled movies and reference patterns | mpv gpu-next/libplacebo | Retain the existing leader. Map decoded HDR into a measured target and evaluate dithering explicitly. Optical target calibration is still missing. |
| First: suitable Linux live games | Gamescope HDR client → SDR output | Strong new workload-specific candidate. Its inspected options distinguish exposing HDR support to applications from forcing PQ output. Application, WSI/Proton/backend compatibility and latency remain untested. |
| Second: Windows movies | MPC-BE + MPC Video Renderer | Practical independent player/renderer comparison before custom development. Profile support and downstream transforms need verification; no original-Pro calibration is implied. |
| Second: live-content feasibility | OBS HDR capture → SDR fullscreen projector | Lower-code prototype for capture and mapping. Must capture genuine unclipped HDR, avoid double mapping, and meet an explicit latency budget. Not a native-PQ test harness. |
| Conditional custom path | Capture + libplacebo, informed by Nightfall | Build only after a baseline demonstrates a missing capability or unacceptable latency/quality. Nightfall is useful implementation evidence, not a ready original-Pro port. |
| Conditional appliance comparator | Pro Neckband | Vendor host processing is relevant, but its first-use glasses update behaviour can invalidate a preserved firmware baseline. Do not connect it for comparison before addressing this dependency. |

Choose the movie and gaming paths independently. Gamescope does not automatically generate stereoscopic views, and a movie player does not solve arbitrary live-game rendering. HDR-source availability is also separate from output mapping: an application that remains in SDR cannot demonstrate HDR-content handling merely because a display flag is enabled.

If the selected host is Windows and live gaming is the priority, start with the capture feasibility question rather than installing Linux solely to reach the top-ranked Linux candidate. If latency or capture compatibility defeats OBS, that is evidence for custom integration or a different supported application path—not a reason to force PQ into an uncharacterized sink.

Source anchors: [Gamescope, OBS, MPC and Nightfall](https://github.com/Kyuugit/bin/blob/1f312101161d279b00713ac3d8c4cab79962cbff/viture-pro-xr-hdr-refresh-20261029/SOURCES-20261101.md#s02-gamescope), [Neckband baseline hazard](https://github.com/Kyuugit/bin/blob/1f312101161d279b00713ac3d8c4cab79962cbff/viture-pro-xr-hdr-refresh-20261029/SOURCES-20261101.md#s08-pro-neckband).

### 2. Native HDR/PQ input and processing

First empirical choice: **one controlled DXGI or minimal DRM/KMS harness**, selected by the available host and observability. First parallel source choice: **exact-model firmware/EDID/control-path analysis**. Documented vendor-control capture follows only when it can resolve a specific interface or persistence question. A writable loader is not yet justified.

The crucial correction is that the LT7911UXC U2 brief's static HDR10 receiver support does not explicitly establish a PQ EOTF or a complete tone-mapping-to-panel implementation. Receiving a signal, advertising support, transforming pixels and producing the intended optical response are different propositions. The brief also does not prove such processing is absent.

Direct KMS can remove a desktop compositor but does not automatically establish wire-pixel invariance. The inspected historical IGT code is a methodological lead, not a recommended executable test suite: some transitions change bpc, tests gate on EDID, and disruptive cases would add confounders. A successful API call, driver metadata property, host CRC or HDR UI is not sufficient proof.

Proceed only with a test capable of distinguishing host conversion from sink processing. Even a positive native-PQ result would leave panel-native precision unresolved. Defer EDID-only “unlock” claims, cross-brand register transplantation, blind commands and firmware patches without a demonstrated mechanism and credible recovery. [Bridge and KMS evidence](https://github.com/Kyuugit/bin/blob/1f312101161d279b00713ac3d8c4cab79962cbff/viture-pro-xr-hdr-refresh-20261029/SOURCES-20261101.md#s06-direct-kms).

### 3. Higher real per-eye refresh at 3840×1080 SBS

Rank **link/topology and mode-transition diagnosis first**, a **controlled timing/blanking/chroma-depth matrix second**, **DSC capability and negotiated-state investigation conditionally third**, and **firmware/internal-path changes last** for practical delivery. Read-only firmware research may continue in parallel.

The new arithmetic does not depend on remembered behaviour. At this raster, 90 Hz RGB8 requires 8.957952 Gbit/s of active samples alone, exceeding two-lane HBR2's 8.64 Gbit/s after 8b/10b coding. At 120 Hz, RGB8 requires 11.943936 Gbit/s while 4:2:2 8-bit requires 7.962624 Gbit/s. The latter is merely not excluded by that active-sample comparison; it is not a demonstrated, accepted, stable or safe original-Pro mode. The actual negotiated link and compression state remain unknown.

This makes transport observation more useful than adopting an alleged 95 Hz / 420 MHz ceiling. The Beast project's original-Pro claims lack the inspected raw Pro timing/optical evidence required here; they remain hypotheses, not independent confirmation. Its active link workaround is not a passive Pro diagnostic.

Keep RGB8 as the image-quality reference. Consider 4:2:2 only when the owner accepts its detail trade-off. Success requires the full transmitted raster and unique frames observed in both eyes. Higher OS refresh, half-SBS, lower transmitted resolution, rendered frame generation or ordinary 2D120 does not meet this goal. [Calculation and refresh findings](https://github.com/Kyuugit/bin/blob/1f312101161d279b00713ac3d8c4cab79962cbff/viture-pro-xr-hdr-refresh-20261029/CONTINUATION-20261101.md#3-full-resolution-sbs-refresh-replace-ceiling-lore-with-discriminating-evidence).

### 4. Headsets gaining HDR after release

There is **no verified strict native-unlock winner in the sources inspected**. This is not a universal nonexistence claim.

The highest-priority firmware lead is exact-model **XREAL 1S / One-family AI HDR beta reporting**. Reports of an option and conflicting reports of visible effects do not establish native PQ. New 1 Pro+ documentation must not be transferred to older models. **Nightfall on Quest** is stronger inspectable implementation evidence for later HDR-stream handling, but its inspected path maps the stream for presentation rather than proving a native panel unlock. **PSVR2 PC experiments** are useful platform/mapping leads, but PSVR2 shipped with HDR on PS5 and therefore fails the strict shipped-without-HDR criterion.

Require exact old/new builds, source transfer and output evidence, plus optical before/after response before promoting a case. Do not buy or update another headset simply to strengthen an analogy. [Precedent evidence and exclusions](https://github.com/Kyuugit/bin/blob/1f312101161d279b00713ac3d8c4cab79962cbff/viture-pro-xr-hdr-refresh-20261029/SOURCES-20261101.md#s11-xreal).

## Decisions still needed

| Owner decision | Why it changes the next step |
|---|---|
| Primary workload and existing host | Movies, live games and streamed content require different capture/rendering paths. Select actual applications/content profiles and OS/GPU before implementation. |
| Success criteria | Set reference-white/peak/gamut goals, acceptable banding/clipping, stereo requirements, and an end-to-end latency budget. A brighter image alone is not the objective. |
| Refresh-quality trade-off | Decide whether full-resolution 4:2:2 is useful or whether RGB text/chroma fidelity is mandatory. Do not choose an arbitrary ceiling or guaranteed target. |
| Measurement access | Establish valid near-eye optical geometry and frame-timing observation before quantitative claims. Available equipment and uncertainty determine what a test can prove. |
| Action boundaries | Authorize specific baseline collection, host changes, installations or captures with rollback as applicable. Firmware/device writes remain a separate decision; none are approved by this research. |

No decision is needed to preserve the evidence, refine source-only analysis or record why an approach was excluded. Fresh public firmware acquisition did not complete in the research environment; repeating static analysis requires available authorized bytes and hash checks, not a flash operation.

## What would change this recommendation

A reproducible original-Pro native-PQ optical result with upstream conditions established would promote native processing. A documented, reachable exact-model processing control would justify narrowly scoped interface work. A measured full-raster both-eye refresh improvement would update the preferred mode for that exact configuration. A host-mapping path failing the declared quality or latency criteria would demote that implementation, not automatically prove that native firmware work is the only alternative.

Conversely, a mode-setting ACK without output, an HDR setting without a verified source, a bridge feature list, or a firmware-version anecdote does not change the recommendation.
